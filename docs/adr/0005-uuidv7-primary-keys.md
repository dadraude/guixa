# 0005 — UUIDv7 primary keys

- Status: accepted
- Date: 2026-10-02

Whenever possible, database rows are identified by a **UUIDv7** primary key generated by the
application (Laravel's `HasUuids` produces time-ordered UUIDv7). UUIDs don't reveal how many
rows exist or let anyone guess other rows' URLs. They can be created on the client before
syncing, which the offline islands (boxes and payments) need for their outbox. And being
time-ordered, they keep index inserts nearly sequential, unlike random UUIDv4.

## Considered options

- **Auto-increment integers:** smallest and simplest, but enumerable in URLs and not
  creatable offline without a mapping step.
- **UUIDv4:** random, so index inserts scatter and tables fragment.
- **ULID:** similar properties, but not a UUID, so it lacks a native column type in
  PostgreSQL.

## Consequences

- Foreign keys are UUID columns. Migrations use Laravel's portable UUID column types, so the
  schema stays portable across database engines.
- Numbers people read or write (such as the **household number**) are separate columns, never
  the primary key.
- Exceptions only where a key adds nothing or the framework owns the table: pivot tables use
  a composite key of their two foreign keys, and framework tables (sessions, cache, jobs,
  failed jobs) keep their default keys.
