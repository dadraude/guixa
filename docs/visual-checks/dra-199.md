# DRA-199 · Manager layout rules

Observed 2026-10-26 in the task worktree. The user approved the T43 member
ordering layout as the pattern for this manager rollout and requested no
screenshot work. Visual judgment remains with the user; this record contains
browser measurements and focused regression results.

## Scope and component plan

The 14 manager pages in the T41 inventory use the existing
`.pilot-layout-page` rule in `resources/css/app.css`. Their direct forms,
sections and lists share the existing `.pilot-layout-panel` surface and
padding definition. Stock and return item empty states use
`.pilot-layout-notice`; the repeated list dividers use `.pilot-list`;
repeated button groups use `.pilot-action-row`. Forms continue to use the
existing shadcn-vue controls in `resources/js/components/ui/` and
`FormSelect.vue`. No component library or page-specific palette was added.

The scoped pages are:

- `Manage/Accounts/Index`, `Manage/Households/{Index,Show}`,
  `Manage/Producers/Index`, `Manage/Cycles/{Index,Show}`, `Manage/Settings`
- `Manage/Stock/{Index,Create,Edit,Movements}`
- `Manage/ReturnItems/{Index,Create,Edit}`

The static spacing check lists all 14 pages in
`resources/js/layout-rules.spec.ts`. It failed on six pages before the
off-grid `gap-3`, `p-3` and `space-y-3` values were migrated. Multi-field
forms use 24 px between field groups and 8 px from labels to inputs/errors;
page sections, panels, lists and action groups follow the accepted layout
rules. Phone date and time inputs use at least 16 px text.

## Text-only rendered check

The existing DRA-192 Vue fixture renders the real manager pages with
deterministic data. Its two empty-state selectors now point to the shared
notice class. Run its Vite server, then the DRA-199 geometry script:

```sh
pnpm build
pnpm exec vp dev --config .vitest/dra192-visual/vite.config.ts --host 127.0.0.1 --port 5181
CHROME_BIN="/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" node .vitest/dra199-visual/measure.mjs
```

The script reads computed page/panel padding and section gaps, measures each
visible control and its label hit area, checks direct-child left alignment,
and calls the shared `measureLayout` probe for overflow and clipping. It
excludes Reka's offscreen native select from visible-target checks; the
visible SelectTrigger is measured as a button. It writes no images.

Result after the manager cycle alignment review: **124 cases, 0 failures**. Every scoped page's populated state was
measured at 375 px light/dark, 1024 px with 200% text light/dark, and 1280 px
light/dark. Empty, inactive, cancelled, long-content, validation, processing,
selected-cycle and dialog states were measured at 375 px with 200% text in
dark mode. All cases had no horizontal overflow and met the page/panel
spacing, shared left edge and visible target-size checks.

## Manager cycle alignment correction

The user's live review found that the cycle header spread Orders and Cancel
cycle apart, the cutoff buttons sat above the input baseline, and the cycle
list card had more inset than the Open a cycle card. A focused browser
regression check first measured a 299 px header action gap, an 11 px cutoff
bottom difference, and 16 px of extra horizontal list-card inset. The
controls now share one action group, the form actions align to the input
bottom, and manager list rows use their parent panel's padding without
another horizontal inset. At both 729 px and 1280 px, the two card insets
match, the action gap is 8 px, and the cutoff bottom difference is 0 px.
No additional screenshots were taken.
