# DRA-199 · Manager layout rules

Observed 2026-10-26 in the task worktree. The user approved the T43 member
ordering layout as the pattern for this manager rollout and requested no
screenshot work. Visual judgment remains with the user; this record contains
browser measurements and focused regression results.

## Scope and component plan

The 14 manager pages in the T41 inventory use the existing
`.pilot-layout-page` rule in `resources/css/app.css`. Their direct forms,
sections and lists share the existing `.pilot-layout-panel` surface and
padding definition. Stock and return item empty states use
`.pilot-layout-notice`; the repeated list dividers use `.pilot-list`;
repeated button groups use `.pilot-action-row`. Forms continue to use the
existing shadcn-vue controls in `resources/js/components/ui/` and
`FormSelect.vue`. No component library or page-specific palette was added.

The scoped pages are:

- `Manage/Accounts/Index`, `Manage/Households/{Index,Show}`,
  `Manage/Producers/Index`, `Manage/Cycles/{Index,Show}`, `Manage/Settings`
- `Manage/Stock/{Index,Create,Edit,Movements}`
- `Manage/ReturnItems/{Index,Create,Edit}`

The static spacing check lists all 14 pages in
`resources/js/layout-rules.spec.ts`. It failed on six pages before the
off-grid `gap-3`, `p-3` and `space-y-3` values were migrated. Multi-field
forms use 24 px between field groups and 8 px from labels to inputs/errors;
page sections, panels, lists and action groups follow the accepted layout
rules. Phone date and time inputs use at least 16 px text.

## Text-only rendered check

The existing DRA-192 Vue fixture renders the real manager pages with
deterministic data. Its two empty-state selectors now point to the shared
notice class. Run its Vite server, then the DRA-199 geometry script:

```sh
pnpm build
pnpm exec vp dev --config .vitest/dra192-visual/vite.config.ts --host 127.0.0.1 --port 5181
CHROME_BIN="/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" node .vitest/dra199-visual/measure.mjs
```

The script reads computed page/panel padding and section gaps, measures each
visible control and its label hit area, checks direct-child left alignment,
and calls the shared `measureLayout` probe for overflow and clipping. It
excludes Reka's offscreen native select from visible-target checks; the
visible SelectTrigger is measured as a button. It writes no images.

Result after the mobile stock review: **133 cases, 0 failures**. Every scoped page's populated state was
measured at 375 px light/dark, 1024 px with 200% text light/dark, and 1280 px
light/dark. Empty, inactive, cancelled, long-content, validation, processing,
selected-cycle and dialog states were measured at 375 px with 200% text in
dark mode. All cases had no horizontal overflow and met the page/panel
spacing, shared left edge and visible target-size checks.

## Manager cycle alignment correction

The user's live review found that the cycle header spread Orders and Cancel
cycle apart, the cutoff buttons sat above the input baseline, and the cycle
list card had more inset than the Open a cycle card. A focused browser
regression check first measured a 299 px header action gap, an 11 px cutoff
bottom difference, and 16 px of extra horizontal list-card inset. The
controls now share one action group, the form actions align to the input
bottom, and manager list rows use their parent panel's padding without
another horizontal inset. At both 729 px and 1280 px, the two card insets
match, the action gap is 8 px, and the cutoff bottom difference is 0 px.
No additional screenshots were taken.

## Manager table card correction

The user's stock preview showed a 697 px wide card with all seven fields in
one column, leaving most of the card empty. The same table rule affected
return items. A focused text-only regression first measured stock at 409 px
high and return items at 243 px high at the 729 px viewport. Their rows now
use two columns when the manager table container is at least 36 rem wide and
three columns from 42 rem to the full-table threshold of 58 rem. The action
cell spans the row. Below 36 rem the phone card remains one column; beyond
58 rem the regular table remains in place.

At 680/729/1024 px viewport widths with 100% text, the stock cards measured
267/204/204 px high and the return-item cards 204/141/141 px high. None
overflowed horizontally. The six added preview cases assert at least two
columns and a bounded card height. The 1024 px cases at 200% text still
reflow to one column, preserving readable space for enlarged content. No
additional screenshots were taken.

## Mobile stock list for larger catalogs

The single stock product previously filled most of a phone viewport because
every field and action was always visible. The phone view now shows compact
rows with product name, unit, available count and price. A native disclosure
opens container count, status and the product actions. Inactive products also
show their status in the closed row. The regular manager table remains in use
from the 640 px viewport breakpoint.

The fixture accepts `many=1` to render 20 stock products. At a 375 × 900 px
viewport with 100% text, each closed row measures 64 px high and nine
summaries fit in the first viewport, with no horizontal overflow. A 320 px
viewport was also checked with the narrow-row reflow. The
text-only regression checks all 20 rows, their initially closed state, at
least four visible summaries, and three 44 px actions when a row opens. It
also checks 200% text reflow and the inactive and long-name states. No new
screenshots were taken.

## Modern Minimal theme request

The user supplied the [Modern Minimal shadcn registry item](https://shadcnstudio.com/r/themes/modern-minimal.json).
Its React `init` command would install `lucide-react` and change the app's
shadcn-vue config, so the theme values were applied to the existing
`.pilot-theme` tokens instead. The opt-in management, member, producer,
settings and authentication screens share the new light/dark palette and
shadows; the guest page and unthemed root tokens are unchanged. Inter, Source
Serif 4 and JetBrains Mono are self-hosted through Fontsource packages.

The registry's light primary and destructive fills give white text only
3.72:1 contrast. Their lightness is lowered from 0.62 to 0.52 and 0.64 to
0.56 respectively, without changing hue or chroma, so their 90% opacity
hover states also keep white text above 4.5:1. Input-edge lightness is
0.66 in light mode and 0.55 in dark mode so the edge remains distinguishable
from its card. The registry omits dark primary, destructive and ring tokens;
they use matching accessible blue/red pairs. The theme's unspecified radius
uses the shadcn base value of 0.625rem. Existing success and warning tokens
remain separate from brand accents.

`CHROME_BIN="/Applications/Google Chrome.app/Contents/MacOS/Google Chrome"
node .vitest/dra199-visual/theme.mjs` measured every text/surface pair at
4.5:1 or better and each input edge/card pair at 3:1 or better, in both
themes, after the fonts loaded. The 133 text-only layout cases still pass
after the theme change. No screenshots were taken; visual acceptance remains
with the user.
