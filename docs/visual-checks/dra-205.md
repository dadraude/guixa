# DRA-205 · translation visual check

## Inventory and component plan

The tracked [manifest](../../resources/js/fixtures/dra-205.visual.json) covers 40 actual
application route and role views plus eight Laravel framework error pages. Dashboard has manager,
member and producer variants; Wallet has manager and member variants. The selected matrix is 48 views,
168 states and 514 cases: every application view at 375 and 1280 px in light/dark at 100% text,
1024 px at 200% text for the existing distinct page patterns, and nondefault states on their owning
pages. Each error status (401, 402, 403, 404, 419, 429, 500, 503) has 375/1280 px system-light
and system-dark cases; the shared 404 layout also has 1024 px at 200% text. Error pages use the
framework's own system font and have no interactive control.

This is a copy migration using the existing `AppSidebarLayout`, `Breadcrumbs`, `NavMain`, `Heading`,
`FormSelect`, `InputError`, `NativeDialog`, and shadcn-vue dialog/sidebar primitives. Authentication
uses `AuthSimpleLayout`; security uses `ManageTwoFactor`, `TwoFactorSetupModal`, `ManagePasskeys` and
`PasskeyRegister`. No product component or style was introduced. Dialogs, inline forms and menu
states use those exact existing components, preserving the current layout and action treatment.

The state names reflect actual UI. Accounts and Producers expose pending invitations in their lists;
Households shows an inactive household and settlement details; Pickup stock and return lines and
Reception manual allocations are inline; the passkey registration is an inline form. The initially
proposed Welcome long-data state was removed because Welcome has no dynamic long-content prop. The
producer Dashboard empty state, Stock Movements empty state and member Wallet error state were removed
because those inputs do not change their owning page's rendered UI. Their baseline and 200% cases
remain. No failed case was removed after a visual run.

The independent review found 26 further real owning states: Profile deletion; Security existing
passkeys, removal and two-factor verification; Reception's actual received-total scope and
overwrite confirmations; Cycle creation without a configured weekday and participant/cycle
confirmation actions; Stock status confirmations; household pending/expired invitations; and
producer unsent availability. Closed and cancelled cycles also render on their actual manager
summary and member order pages. The original 462 cases remain. A proposed separate Profile
`delete-long` state was removed before execution because its fixed long translated paragraph is
already present in the deletion dialog at 1024 px/200% text. The passkey removal failure state
performs a failed Inertia request and checks that the action becomes enabled again; the current
product component displays no error copy for that failure, so this state tests recovery of its
control, not an invented notification. Existing inactive-household and completed-pickup states
cover those changed branches.

## Fixture and state truth

[The application fixture](../../resources/js/fixtures/dra-205-visual.ts) imports the actual pages and
layouts, installs the same shared Catalan translator, and selects deterministic role and data props.
Form error and pending states use Inertia's real `Form` request state through a fixture-only HTTP
client; the request never reaches a product server. Dialog and menu states activate their real
controls. Every nondefault state sets its `data-visual-ready` marker only after checking its owning
DOM, such as the visible validation message, disabled submit button, open dialog, populated inline
row, changed role content or long name. The manifest also waits for real open overlay surfaces to
settle. This fixture demonstrates presentation and interaction states, not persistence.

Framework errors are generated by
[RenderErrorPages.php](../../tests/Support/Translations/RenderErrorPages.php), which boots this
worktree's Laravel application with `ca` and debug off and requests its real HTTP exception renderer.
The generated HTML is outside tracked source at `/private/tmp/dra205-real-errors`. The
[fixture-only Vite middleware](../../resources/js/fixtures/dra-205.vite.config.ts) serves that HTML
unchanged except for a test-only mode, text-size and ready-marker script. It rejects a generation
whose Git HEAD or committed `errors/minimal.blade.php` hash differs from the running source. No
product route or duplicate error markup was added. The error-page `lang` attribute is supplied by
the actual Blade template.

Open overlay states measure their visible native `dialog[open]` or portaled `[role="dialog"]`
surface. The dialog selectors include title, description, form, paragraph, field and action text;
the Appearance state measures its portaled menu and option labels. The close glyph's clipped
screen-reader-only name remains in the DOM and its keyboard target is checked separately. Native
select option text belongs to the browser picker; the 1 px serialization select is not the visible
control. The dialog geometry probe measures its label and surrounding form, while the real
`FormSelect` combobox trigger measures 303×44 px at 375 px and 888×74 px at 1024 px/200% text.
No background-page
geometry stands in for an open overlay.

## First validation and measured corrections

The first full candidate at `4385982500408b5f64c8e53921160fe71eab67c1` passed 425 of 462
cases and failed 37. Eight empty notices needed their actual owning notice as the measured panel;
ten open dialogs and menus needed their visible focus targets; and ten auth pending captures waited
for an intentionally continuous spinner. The disabled button and pending marker remain required,
while the settled surface is the stable auth heading. The Login pending state additionally checks
the browser's reduced-motion preference. No failed case was removed.

The Stock long-name case revealed actual ellipsis. The name now wraps in its existing button:
at 375 px the text span's client and scroll widths both measure 106 px, and at 1024 px with 200%
text they both measure 265 px; every text rect stays within the button and the document has no
horizontal overflow. The button retains the complete accessible name.

The Wallet fixture now uses the HTTP adapter's actual `Y-m-d H:i` cooperative local wall-time
contract, and the page formats it as Catalan calendar text without changing its hour. At 1024 px
and 200% text, the visible movement row occupies x=527–927 and its cells x=544–910, each with
equal client and scroll widths (366 px); the document width is 1024 px. The hidden semantic
`thead` is a 1 px, clipped accessibility header whose unlaid-out text ranges extend to x=1159.
`measureLayout` walks those ranges when a whole section is selected, despite the header being
intentionally visually hidden. The Wallet visual panel selector therefore measures the actual
visible forms, notice and card rows; the semantic header remains in the page for table navigation.
The fixture marks the four real `th` elements for measurement only when their computed `clip-path`
is `none` and their header has visible width (four marked at 1280 px, zero at 1024 px/200%). The
ordinary desktop header and every visible card cell remain in geometry checks. No Wallet stylesheet
change was needed.

Keyboard coverage uses fixture-only markers on the first and last actual, enabled page or form
controls in each state (excluding breadcrumb links), as well as the sidebar trigger. Native dialogs and the two-factor modal use
their first and last controls inside the open overlay. The appearance menu receives keyboard focus
on its menu container; ArrowDown reaches the real `menuitemradio` “Clar” with a 44 px height,
`:focus-visible` and a solid outline. Read-only Cycle Show, Producer Cycle Summary and member Wallet
pages have no main content controls; their sidebar remains the keyboard target. Accounts and Orders
empty states likewise have no page action. Welcome uses its real primary action. These are bounded
DOM observations, not exemptions for hidden controls.

Focused browser probes at 375 px measured the below-fold Pickup action at 44 px high (initial
y=1855, then y=815 after keyboard focus), and the long-content Wallet return link at 44 px high
(initial y=1328, then y=832 after keyboard focus); both showed a solid `:focus-visible` outline.
The Stock create action also measured 44 px with visible keyboard focus. Accounts' 24 px native
checkbox sits inside its 44 px label hit area.

The second full candidate at `8754bca7e2c1acee5513592f4e34c2721a70d9b7` passed 456 of
462 cases. Its six remaining failures were keyboard fixture expectations: the Cycle and Stock
dialogs each selected an action inside a **closed** native `details` disclosure as the last target,
and the open Appearance menu was expected to be reachable by Tab although its option focus uses
ArrowDown. The fixture now excludes descendants of closed disclosures and selects the visible
native `summary` instead. A real Tab reached Cycle “Altres accions” in one step and Stock “Estat i
historial” in four steps from the close button; both summaries measured 44 px and showed solid
`:focus-visible` outlines. The hidden cancel/deactivate buttons are no longer marked.

The open Appearance state dispatches ArrowDown and requires an actual focused `menuitemradio`
inside the open menu, a computed minimum height of at least 44 px and an actual rect height of at
least 44 px before its ready marker. The baseline Appearance case still Tabs to the 44 px
appearance trigger. The open menu records a state-specific no-Tab reason because Tab dismisses its
roving-focus menu. No view, state or case was removed.

The user-authorized third full run at `181d9468470c0e523355521182a2487c45d8917f` passed
460 of 462 cases. Both Appearance-menu states timed out at the ready marker: in the headless
runner, the synthetic ArrowDown focused the real “Clar” radio option and the menu/size checks
passed, but `document.hasFocus()` and `:focus-visible` remained false. At 375 px its computed

CDP ArrowDown moved focus to “Fosc”, made `document.hasFocus()` and `:focus-visible` true, and

headless window modality from a product focus defect. The user-authorized fourth full run at
`a16d682084dc79df71e11634b1a05271988f31f2` passed and verified all 462 cases. That report
remains retained separately from the expanded review candidate.

Before the 514-case committed run, focused browser diagnostics exercised all 26 added states at
